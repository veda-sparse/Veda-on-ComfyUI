# 核心：布局、tile、方案、打分与选择

## 目标

在 ComfyUI 的 H3 打包序列上，复现 Veda 训练时的块选择，结果与设备、后端无关。

## 设计与不变量

- **规则是契约**：tile 排列（`core/tiling.py`）、方案表（`core/plans.py`）、打分
  （`core/predictor.py`）和选择（`core/selection.py`）与 Miowtion 训练 / 搜索时完全一致，改动
  它们等于让打分器面对没见过的输入。改之前先和 Miowtion 对齐。
- **布局映射**（`core/h3_layout.py`）：ComfyUI 的打包顺序与 Miowtion 相同：
  `text | cond（关键帧/引导帧） | 参考 | 目标音频 | 目标视频`，没有 padding 行。
  - target = `video` 段，网格 `(latent_t, latent_h/2, latent_w/2)` 来自 `layout.signature`；
  - reference = `cond` 与 `ref_img` 段，网格从 `position_ids` 恢复，并逐行校验是 T,H,W 行优先；
    校验不过的段保持 global（全注意力，永远正确，只是慢一点），并记在 `LayoutSpec.skipped`；
  - 文本和所有音频段是 global 行。
- **tile**：每个 tile 128 行，tile 形状 (t,h,w) 的乘积为 128；真实行压在 tile 前部
  （`valid_count` 前缀），padding 槽位为 -1 / 0。reference 段用最少 padding 的形状
  （Miowtion 对 tiled conditions 的规则），target 用方案表里每层每头的形状（每层最多两种）。
- **方案选择**（按目标 token 网格）：纵横比最近（含 H/W 转置）→ 时长（latent_t）最近 → padding
  最少；完全匹配时自然选中。永远能选出方案；非精确匹配时在节点上说明。
- **选择规则**（见 `selection.py` 模块注释 1–7）：global 双向全保留；只有 video→video 象限
  稀疏；比例预算按等 kernel 代价 `ratio * n_ideal^2 / n_cols`；小数部分按 Bresenham 分摊；
  对角 tile 强制保留并占预算；空 tile 不选；reference 与 generated 两个列块各自 top-k、各自预算。
- **引擎**（`core/engine.py`）：每个头组 gather → pool → logits → select → mask → 后端 →
  scatter；按头分块，一份 tile 顺序副本不超过 `clamp(free/16, 64 MB, 1 GB)`（CUDA）或 256 MB。
  统计（保留比例）累加在设备上，运行结束才读一次，不在热路径上同步。

## 代码位置与接口

`veda_comfy/core/*`，不 import ComfyUI；`engine.VedaEngine.attention(q, k, v, layer, spec, plan)`，
q/k/v 为 `[S, H, D]` 视图。

## 预算：固定 tile 数，不用比例

每个 query tile 保留固定数量的 key tile，默认 **32 个**。以前是等代价比例（90% 稀疏），
但保留数会随网格面积一起缩放：双采工作流的第一段跑在训练网格的 0.33 倍上，90% 稀疏只剩
5.5 个 tile。5.5 不是整数，余数由 Bresenham 在行之间摊，而 tile 顺序里 t 块变化最快
（`tiling.span_tiles` 的 `permute(2,4,0,1,3,5)`），**相邻行就是时间上相邻的块**——每隔一个
时间块上下文就差 20%。绝对数量不随网格变化，也没有余数。

（必须说清楚：这个"相邻时间块差 20%"的机制真实存在，但**实测没有产生可见闪烁**，
见 hardware.md。改成固定数是因为预算不该随网格塌陷，不是因为它修好了闪烁。）

## Sol 的池化误差修正：测过，不采用

给每个被跳过的 tile 补一项（池化均值 key + 求和 value）融进同一个 softmax。参考实现
`reference.pooled_correction_attention` 留着，Triton kernel 写过、与 fp32 参考对齐到
1e-4，**然后删掉了**。

**理由是另一组在真实模型上的消融**：等算力下（让不补偿的一方多选块）**逐头配对**，补偿的
ε 比值中位数只有 0.988~0.998，即只好 1% 左右；约 2% 的头灾难性变差（最差 −424%，集中在
第 0、1 层，均场近似最差处）。把权重换成精确的 `E_uj`（任何权重预测器的等成本上界）
在 ρ=20% 时只剩 +1.4%，密度越高越差——瓶颈在块内**方向**不在权重，而修方向就是 VSA
粗粒度分支，本仓库已知它 fully train 后无收益。

**我自己那次测量是错的，记下来当教训。** 我用 `torch.randn` 造 q/k/v 和打分，测出等时间下
误差 1.28 → 0.42（3 倍）并据此说它值得做。但 i.i.d. 高斯的 q/k **几乎没有集中度**：实测
72 个 tile 里 top-8 只占 12.7% 的注意力质量，均匀是 11.1%。那个设置落在"稀疏注意力根本
不适用"的区间，而补偿项恰好擅长兜住均匀的 bulk——它衡量的是一个不存在的场景。真实注意力
高度集中，这正是 Veda 成立的前提。

两条教训：
- **合成张量不能用来评估稀疏方法的收益**，必须有真实激活的集中度；
- **等成本对比必须逐头配对**，按中位数之比会把差距放大（14.7% vs 实际 1%）。

### 在双采几何上自己复测（真实激活）

`tools/selection_ablation.py` + 一个临时的捕获 shim，从真实渲染里抓 q/k/v/layout/打分，
按真实激活评估。两段几何各 3 个 capture（层 10/25/40）× 8 头 = 24 头，逐头配对：

**第一段 8x14x72（72 tile，补齐 10%）**

| 规则 | 每行保留 | 平均误差 | 配对中位比 | 更好的头 |
|---|---|---|---|---|
| top-k 44% | 32.0 | 0.1122 | — | — |
| top-k + logB 44% | 32.0 | 0.1153 | 0.9993 | 50.0% |
| adaptive tau 1.3 | 8.7 | 0.3212 | — | — |

**第二段 15x27x72（252 tile，补齐 14%）**

| 规则 | 每行保留 | 平均误差 | 配对中位比 | 更好的头 |
|---|---|---|---|---|
| top-k 25% | 63.0 | 0.1073 | — | — |
| top-k + logB 25% | 63.0 | 0.1083 | 1.0031 | 41.7% |
| adaptive tau 1.3 | 26.9 | 0.1977 | — | — |

两条结论：

- **`log B` 在这里没有收益**，两个几何上都是中位比 ≈ 1.00、更好的头约一半或更少，平均误差
  还略差。对方在 16:9@37（366 tile、ρ≤20%）上测到补回 22~36% 的 oracle 差距，**在双采的
  小网格上没有复现**。他们自己标注过"收益直接取决于补齐块的比例"——而这里补齐 10~14% 反而
  比他们那边高，所以不是补齐太少的问题。
- **adaptive 在等保留数下不占优**：第二段保留 26.9 个 tile、误差 0.1977，而 top-k 在 27 个
  tile 附近插值约 0.19。与对方在真实模型上的结论一致。

样本量要说清楚：24 个头、每个几何一步一个 seed，对方是 134400 行 × 4 个去噪步。这组只够
说"在这个 regime 没看到收益"，不足以反证他们在 16:9@37 上的测量。

### adaptive 也要重新看

同一组消融里，可变预算（z-score 阈值，即我们的 `adaptive`）在真实代理分数下**全面不如固定
top-k**：ρ=5% 时 0.3478 对 0.3773，10% 时 0.2211 对 0.2250，20% 时持平；即使用 oracle
分数，ρ=5% 仍是 −2.2%。另有一笔没算进 ε 的成本：**负载不均衡**，固定 top-k 的 max/mean 是
1.006~1.059，阈值规则是 1.10~2.03，对 kernel 是实打实的尾部开销。

所以 `adaptive` 保持**非默认**，并且在没有在真实模型上复测之前不应推荐。默认仍是
`fixed` + 32 tile。
